# Joy Phase Roadmap

**Last updated:** 2026-10-16  
**Planned scope:** 72 focused PRs (#24–#95), subject to adjustment after implementation and test results. The C++/NDK phase is planned after the joy, math-strategy, Lua localization, and LiveOps locale work; build-channel-aware updating follows as a separate delivery-system task. Multiplayer is a later, opt-in phase and starts with local-network peer-to-peer play.

The goal is to make GuessTheNumber feel more rewarding and lively while growing it beyond random guessing into number sense and efficient mathematical strategy, without destabilizing existing gameplay, saves, localization, or offline behavior. Keep changes focused and validate each PR before continuing.

**Status note (2026-10-14):** This roadmap tracks intended scope, not proof that every feature is merged. Items marked implemented are supported by the current `master` changelog; partial implementations are labeled as such. Work found only on feature branches must not be marked complete until it lands on `master` and its checks are reviewed.

## Cross-platform sameness and proposed shared-web UI direction (2026-10-17)

**The product requirement remains an exact same-game experience across platforms.** The proposed implementation is one HTML/CSS/JavaScript frontend for player-facing screens, Kotlin/KMP as the trusted game engine, and thin native host adapters. This is a proposed architecture, not a claim that the migration has shipped. See [Shared Web UI Architecture](../../docs/SHARED_WEB_UI_ARCHITECTURE.md) for the bridge contract, platform map and exit gates.

- Follow the single, sequential five-stage delivery order in [Windows Feature Parity Plan](../../docs/WINDOWS_FEATURE_PARITY_PLAN.md). That document owns the Windows parity matrix, stage gates and evidence; this roadmap must not create a competing Windows phase list.
- Match Android screens and reachable interactions: content, hierarchy, labels, controls, menus, dialogs, navigation, locked/unlocked states, loading/empty/error states, progression, rewards, settings meaning, localization, save behavior and offline play.
- Keep authoritative Kotlin/KMP rules, models/contracts, validation and transaction logic shared.
- Prefer one canonical HTML/CSS/JavaScript frontend for player-facing screens after a prototype proves the approach. Keep Compose for native/system surfaces rather than duplicating the shared game UI.
- Reuse canonical assets and localization sources instead of maintaining separate platform copies.
- Cordova is a candidate for supported mobile platforms; Windows needs a maintained embedded WebView host, not the unmaintained Cordova Windows platform.
- Keep Android and Windows host adapters thin and platform-specific: lifecycle, storage, audio, notifications, input/focus, windowing, update/install and packaging. Do not move platform APIs into common code merely to increase code sharing, and do not duplicate authoritative game rules in the Windows host.
- Desktop adaptations may change input mechanics and layout for resizable windows, keyboard, mouse, hover and focus. They must preserve feature availability and meaning. Any intentional feature difference needs a documented reason and explicit classification in the parity matrix.
- Preserve existing Android save compatibility, offline-first behavior, and the no-ads/no-analytics/no-accounts requirement.
- Keep evidence honest: merged source, CI, unit tests, Windows runtime checks, screenshot comparisons and installer tests are different evidence types. A passing build is not proof of visual/runtime parity. Never mark a row verified without evidence for the exact candidate.
- Do not skip a stage gate or mark the Windows port complete while required parity rows remain unverified, blocked or unexplained.

**Platform-specific exception policy:** the project owner decides which platform-specific features are allowed. QoL, UI, accessibility and OS integrations may be adapted for each platform; platform-specific gameplay is also allowed when the owner explicitly approves it. Record each exception, its reason, approval and verification plan in the Windows parity matrix. Do not silently change shared balance, progression, rewards or save semantics.

**Current Windows status (2026-10-17):** the KMP foundation milestone is recorded separately in [KMP Foundation Status](../../docs/KMP_FOUNDATION_STATUS.md). Windows feature parity remains in progress; route coverage is not proof of full screen implementation or runtime parity. A shared-web UI migration is proposed and must not be marked implemented until the prototype, bridge validation, runtime checks and rollback gates pass. PRs #217–#222 are merged with their required Android/Windows CI passing. PR #220 implements all six permanent Prestige/Ultra effects in shared rules, centralizes achievement rewards, adds the Arcade reward transaction adapter and desktop-only scrollable quick-access navigation. PR #221 adds all five Android Arcade minigames with the canonical catalog and shared reward transaction. PR #222 fixes the nested-scroll exception in the Arcade route; the owner confirmed Arcade opens successfully in the Windows app. Remaining gaps include the Windows Music Player placeholder, Talent Web localization, runtime verification of PR #220's upgrade/navigation behavior and individual Arcade minigame rewards/persistence. Continue with the existing parity plan rather than creating duplicate extraction work.

## Temporary LiveOps locale pack design

LiveOps may deliver **translation data only**, for example locale ID, pack ID, version, expiry, and a map of approved translation keys to localized strings. This data must not be treated as executable Lua or remotely downloaded code.

Expected flow:

1. LiveOps supplies a versioned temporary locale pack.
2. Kotlin validates its schema, locale, approved key set, size, version, and expiry.
3. The app activates and caches the accepted pack.
4. Lua scripts return approved localization keys and formatting arguments; Kotlin resolves them using the active locale and valid downloaded pack.
5. If a pack is missing, invalid, unavailable offline, or expired, the app uses the built-in locale and existing fallback rules. Built-in translations are never overwritten.

**Installed-app requirement:** the downloader, validator, cache/expiry handling, and locale resolver must already exist in the installed app. LiveOps cannot add these capabilities to an older APK on its own.

## Architecture and acceptance rules

- Kotlin remains authoritative for locale resolution, payload validation, lifecycle, persistence, eligibility, and rewards.
- Lua remains sandboxed and must not gain direct reward/save mutation capabilities.
- Preserve existing save compatibility, reward rules, claim limits, and offline play.
- Every player-facing string, including Lua activity and random-event text, must use the localization system.
- Test language switching, formatting arguments, missing/malformed translations, pack expiry, corrupted packs, offline startup, and fallback behavior.
- Build updates must be channel-aware: production uses GitHub Releases; debug uses the designated stable Debug APK from GitHub Actions artifacts. Keep release and debug update feeds separate and identify the active channel in About. When a newer compatible build is found, show a localized **Update available** state and let the user choose whether to install; hide or clear that state when the update is no longer available or compatible.
- Define how the stable debug artifact is selected and retrieved, including artifact retention/expiry, metadata, version compatibility, access limits, and integrity verification. Treat the Actions artifact as a ZIP container: validate the archive entries, reject unexpected paths or multiple ambiguous APK candidates, extract the designated APK and required metadata to app-controlled storage, then verify package ID, version, signing certificate/update compatibility, and checksum/signature before launching Android's package installer. Never install or trust the ZIP as an APK. Do not assume an Actions artifact is permanent or anonymously downloadable.
- Test update discovery and failure cases for both Debug and Release variants. Updating must remain optional and offline gameplay must continue to work.
- Refresh LiveOps quietly when the app opens or returns to the foreground, then approximately every 5–10 minutes while the app remains active when practical. Use lifecycle-aware scheduling rather than keeping background work alive solely for a timer; avoid overlapping requests, use conditional requests/caching where supported, respect connectivity and server rate limits, and back off after failures. LiveOps refresh must not interrupt gameplay or show update-install prompts. Apply only validated, trusted LiveOps data and retain the last valid cache/bundled fallback when refresh fails.

## Planned C++/NDK engine integration (#40–#45)

The project will plan a staged native-engine integration rather than rewriting the whole app in C++. Kotlin remains the application and gameplay authority. C++/NDK is intended for a narrowly scoped engine computation with a clear reason to be native; it must not become a second source of truth for game state.

- Start with an architecture audit and Kotlin baseline tests/measurements.
- Add CMake/NDK scaffolding independently from gameplay changes.
- Introduce a small JNI boundary with validated inputs, explicit errors, and a Kotlin fallback.
- Port one bounded deterministic component at a time, after confirming the selected boundary fits the existing engine.
- Add parity, ABI, failure-path, and regression tests before relying on native results.
- Keep persistence, UI, localization, LiveOps networking, eligibility, and authoritative reward settlement in Kotlin.
- Preserve the Lua sandbox. Lua must not gain direct JNI/native access or unrestricted save/reward mutation.
- Native code must not be described as a performance improvement without measurements. If profiling does not justify a native component, document the result and keep the integration minimal rather than adding complexity for its own sake.
- Verify supported ABIs and the actual NDK/CMake configuration before implementation; do not assume a particular ABI is available.
