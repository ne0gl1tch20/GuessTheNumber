# Lua LiveOps Bundle Format

A copy-ready repository scaffold, sample script, signing helper and manual publishing workflow live in [`liveops-template/`](../liveops-template/README.md). Copy its contents into the separate content repository before enabling remote updates.

The Lua Activity Hub is exposed from the app's **More** menu when the bundled `lua_scripting` feature flag is enabled, including release builds. The developer console remains debug-only. Keep the flag disabled if the activity hub is not ready for a given distribution.

The Android client reads the HTTPS URL configured by `luaLiveOpsManifestUrl`. The default points to [`ne0gl1tch20/GuessTheNumber-LiveOps`](https://github.com/ne0gl1tch20/GuessTheNumber-LiveOps), which publishes the signed manifest and its source scripts.

## Repository layout

```text
manifest.json                 # signed envelope generated by the publisher
payload.json                  # unsigned source payload used by the publisher
scripts/
  example_event.lua
```

The signed envelope has exactly two fields:

```json
{
  "payloadBase64": "BASE64_OF_EXACT_UTF8_PAYLOAD_BYTES",
  "signatureBase64": "BASE64_RSA_SHA256_SIGNATURE"
}
```

The RSA signature is `SHA256withRSA` over the decoded `payloadBase64` bytes. Do not parse and reserialize the payload after signing. Each script has a lowercase SHA-256 hash of its exact UTF-8 bytes.

## Payload fields

- `schemaVersion`: currently `1`
- `hostApiVersion`: currently `1`
- `minAppVersionCode` and `maxAppVersionCode`: compatible app version-code range
- `bundleVersion`: monotonically increasing positive integer
- `scripts`: 1 to 50 unique entries

Each script entry contains `id`, `fileName`, `title`, `description`, `sha256`, `featured`, `hostApiVersion` and `capabilities`. IDs must match `[a-z0-9_-]{1,64}`; file names must be plain `.lua` names without directories; the initial allowed capability is only `log`. Each script must return a bounded activity table with `title`, `description`, `prompt`, `options`, `correct_option`, `success_message` and `failure_message`, matching the bundled Number Rush sample. `options` must contain 2–6 answers and `correct_option` is a 1-based index. Remote scripts cannot grant rewards or modify saves.

## Signing key setup

Generate an RSA signing key outside the repository and keep the private key in a protected secret store:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out lua-liveops-private.pem
openssl pkey -in lua-liveops-private.pem -pubout -outform DER | base64 -w0
```

Pass the printed DER public-key Base64 to the app build as `-PluaLiveOpsPublicKeyBase64=...`, or store it as the app repository Actions secret `LUA_LIVEOPS_PUBLIC_KEY_BASE64` for manual APK builds. Never commit the private key. The Android client fails closed if the public key is missing or a signature/hash/API/version check fails.

## Publish a bundle

From the content repository, run:

```sh
python3 tools/sign_lua_liveops_bundle.py --payload payload.json --scripts-dir scripts --private-key "$LUA_LIVEOPS_PRIVATE_KEY" --output manifest.json
```

The private-key environment variable should contain a path to the protected PEM file. Commit the generated manifest and the referenced scripts together. Increase `bundleVersion` for every published change. Keep prior Git tags/commits so a known-good bundle can be restored.

The app stages and validates all files, then re-verifies the staged manifest and every staged script before changing its active-bundle pointer. The previous bundle directory is retained and can be selected automatically if a featured script fails. A separate highest-accepted-version marker prevents recovery from weakening version checks. The current sandbox limits source size and interpreted instructions but does not enforce a hard heap-memory cap, so publish only trusted scripts until on-device memory behavior is validated. For localized activity copy, use English strings already present in the app locale catalog; new arbitrary LiveOps copy currently falls back to its English text. Online delivery is optional; bundled scripts remain usable without a connection.


## Bundle version and refresh behavior

Treat `bundleVersion` as a monotonically increasing publication number, not a script count or app version:

- Start at a positive integer and increment it whenever publishing changed payload or script content.
- The client accepts a version newer than the active bundle and retains the previous bundle for rollback.
- Refreshing the exact version already active is an idempotent no-op. The app reports that the bundle is already up to date rather than repeatedly warning.
- A version older than the highest accepted bundle version is rejected, even if recovery temporarily points the app at an older cached bundle.
- The highest accepted version is stored separately from the active pointer. Recovery can switch the active pointer to a previously verified bundle without lowering the anti-rollback high-water mark.
- If you need to restore older content, republish that content under a new, higher bundle version rather than lowering the version number.
- The publisher validates IDs, filenames, metadata, capabilities, UTF-8 source and source size. It rejects duplicate filenames and refuses to publish changed payload bytes at the same or a lower bundle version.

For the current LiveOps repository, bundle version `2` is the first publication with the valid Welcome activity. Publish through the content repository's GitHub Actions workflow after merging changes to `main`; confirm the workflow succeeds before testing refresh in the app.

## Activity script contract

A Lua activity file must return a table as its final result. Minimal shape:

```lua
return {
    title = "Welcome to LiveOps",
    description = "A short activity description.",
    prompt = "Which statement is correct?",
    options = { "Correct answer", "Incorrect answer" },
    correct_option = 1,
    success_message = "Correct!",
    failure_message = "Try again."
}
```

Keep `correct_option` within the 1-based range of `options`. A script that only logs messages, returns no value, or returns a non-table is rejected by the activity loader and the app may fall back to the bundled featured activity. Logging with `gtn.log(...)` is useful for diagnostics, but does not replace the returned table.
